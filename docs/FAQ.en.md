## Runtime and environment

### Q1: The app cannot find Python or the Engine. What should I do?

Run the runtime check from the repository root:

```bash
.venv/bin/python scripts/check_runtime.py \
  --root . \
  --python .venv/bin/python \
  --model models/bball_model.pt
```

You can explicitly configure a development run:

```bash
BHE_REPO_ROOT="/path/to/basketball-highlight-editor" \
BHE_PYTHON="/path/to/basketball-highlight-editor/.venv/bin/python" \
flutter run -d macos
```

A distributable `.app` should contain the Engine and Python under `Contents/Resources/runtime`; it must not depend on developer-specific absolute paths. See [GETTING_STARTED.en.md](GETTING_STARTED.en.md) for lookup order.

### Q2: What does the Swift Package Manager warning for `media_kit_libs_macos_video` and `media_kit_video` mean?

It is a Flutter compatibility notice about the plugin dependency integration method on macOS. It is not, by itself, proof that the current app failed. If the existing CocoaPods/traditional integration still works, continue functional validation while tracking the warning.

Act when:

- a future Flutter version turns the notice into a build error;
- the project switches to Swift Package Manager;
- `flutter build macos` or Xcode actually fails.

Then prefer a plugin release with SPM support or contact the maintainers. Do not delete the video plugins just to remove the warning. After upgrading, run `flutter pub get`, `flutter analyze`, `flutter test`, and a macOS build.

### Q3: Why not use `.tooling/flutter` from the repository?

`.tooling/` is a machine-local SDK and is ignored by Git. Public documentation uses `flutter` on `PATH`; developers should provide a compatible SDK. Use `FLUTTER_BIN` or an absolute path when a local setup requires it.

### Q4: Why does the runtime checker report a missing model?

Confirm the exact convention:

```text
models/bball_model.pt
```

Or pass a custom model:

```bash
.venv/bin/python scripts/check_runtime.py \
  --root . \
  --python .venv/bin/python \
  --model /absolute/path/to/your-model.pt
```

The weights must have compatible class names and be authorized for your use. The source preview does not provide model weights and does not download unknown weights.

### Q5: Why are both FFmpeg and FFprobe required?

FFprobe reads duration and other metadata. FFmpeg creates analysis proxies, previews, and exports. Check them with:

```bash
which ffmpeg
which ffprobe
ffmpeg -version
ffprobe -version
```

For distribution, do not copy a Homebrew binary that depends on machine-local dynamic libraries; see [MACOS_PACKAGING_V1.md](MACOS_PACKAGING_V1.md).

## Analysis and candidates

### Q6: Analysis completed but there are no candidates. Is that normal?

An empty list is not necessarily a UI bug. Check, in order:

1. the source video plays correctly;
2. the model contains the classes required by the current pipeline, such as `basketball` and `hoop`;
3. the ROI covers the hoop and ball movement, not only a tiny rim edge;
4. the analysis range is not accidentally very short;
5. the model and video codec are compatible;
6. the Engine did not report `NO_BALL_DETECTIONS`, `MODEL_LOAD_FAILED`, or `ANALYSIS_FAILED`.

Start with a larger ROI and a short sample. If Standard produces candidates but Fast does not, rerun Standard instead of treating Fast as complete ground truth.

### Q7: Why is one candidate several minutes long?

A candidate is an event window generated by model evidence and rules, not a final edited clip. Confirm the event time in the review workspace, then adjust the clip start and end. Also check whether the ROI is too large, the model is treating player/rim motion as ball events, or the video has timestamp problems.

Do not edit candidate JSON or SQLite manually; use the UI so review and export state remain consistent.

### Q8: What is the difference between Fast and Standard?

Standard includes source-video refinement and favors quality. Fast uses a lower-cost proxy and skips refinement, so it favors speed and may miss events. Fast is not a latency guarantee or a more accurate mode. See [research/ANALYSIS_MODES_V1.md](research/ANALYSIS_MODES_V1.md).

### Q9: Can I export or switch modes while analysis is running?

Only one heavy analysis or export job runs per project. You can keep viewing and reviewing the previous completed candidates while a new analysis is running, but export is locked. Cancel the current job before switching modes. The previous result is not cleared until the new result is validated and committed.

### Q10: Why can I no longer edit the review area after clicking Export?

Export reads the current database state and locks candidate writes that would change the export input. This prevents the exported file from disagreeing with the visible review state. Retry failed exports; after an export finishes, you can edit and start another export.

## Video, projects, and data

### Q11: What if the source video was moved or deleted?

The project stores a path and metadata instead of copying the source video. Use the relink action to select the new path. If content or important metadata changed, recalibrate the ROI before analyzing again.

### Q12: What can be cleaned from a project directory?

Usually rebuildable items include proxies, detection caches, and failed-job temporary files. Do not automatically delete:

- the source video;
- `project.db`;
- review records;
- exports the user chose to keep.

See [architecture/PROJECT_LAYOUT_V1.md](architecture/PROJECT_LAYOUT_V1.md).

### Q13: Why are models, videos, and screenshots absent from GitHub?

This is intentional. Weights, real game videos, labels, and development screenshots can contain unverified rights, personal information, or local paths. The public repository keeps source and usage instructions; public demos must use cleared assets.

### Q14: Does reviewed-data export upload anything?

No. `scripts/export_review_dataset.py` reads the local project database and writes JSONL/CSV locally. The result may contain real paths, notes, or player information, so keep it local and do not commit it.

## Build and release

### Q15: Does a successful `flutter build macos` mean the app is ready to distribute?

No. The `.app` still needs portable Python and dependencies, FFmpeg/FFprobe, a model, notices, signing, notarization, and clean-machine validation. See [RELEASE.en.md](RELEASE.en.md).

### Q16: Why not rewrite the Python Engine in Rust now?

The main costs are model inference, video decoding, and FFmpeg, not the JSONL service itself. V1 stabilizes the Python Engine, protocol, and SQLite contract first. A future Rust Engine can preserve those contracts; Rust is not a current open-source runtime prerequisite.

### Q17: How do I report a security issue?

Do not publish exploitable details, video samples, or secrets in a public issue. Read [SECURITY.md](../SECURITY.md) and use GitHub private vulnerability reporting if enabled, or the maintainer's published security contact.

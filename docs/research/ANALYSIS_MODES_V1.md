# 分析模式与性能优化 V1 决策记录

> 本文记录 2026-08-12 已确认的产品和工程决策，作为后续实现与上下文恢复的依据。
> 本文同时记录第一期已落地的实现边界；质量闸门和真实视频基准仍需在功能正式开放前完成。

## 1. 目标

在不改变候选审核、手动调整和导出基本规则的前提下，增加两档分析模式：

- **标准模式**：质量优先，执行完整分析链路。
- **快速模式**：速度优先，允许少量漏检，用户可以随后用标准模式重新分析。

当前已知主要耗时来自代理生成、YOLO 粗扫、视频解码和原视频回源精筛。快速模式优先减少这些成本，不通过减少候选数量来制造“变快”。当前桌面入口默认可见；发布构建可以通过 `ENABLE_FAST_ANALYSIS=false` 隐藏。

本文件的决策状态：**第一期协议、引擎和审核状态闭环已实现；性能与召回率基准待实测**。

## 2. 已确认的模式规则

| 项目 | 标准模式 | 快速模式 |
|---|---|---|
| 首次默认 | 是 | 否 |
| 项目记忆 | 按项目记忆上次选择 | 按项目记忆上次选择 |
| 代理规格 | 当前标准参数 | 固定 `640×480 / 3 FPS`，保持原视频宽高比 |
| 原视频回源精筛 | 执行 | 跳过 |
| 模型与检测阈值 | 当前标准参数 | 与标准模式相同，暂不换模型、不改阈值 |
| 候选业务规则 | 保持现有规则 | 与标准模式保持一致 |
| 候选数量 | 不人为限制 | 不人为限制 |
| 快速候选来源 | 精筛后的 refined candidates | 粗扫 `coarse_candidates.json`，证据标记 `analysis_source: coarse` |
| 审核播放 | 原视频 | 原视频 |
| 结果风险 | 质量优先 | 明确提示可能少量漏检 |

快速模式的具体粗扫参数、缓存命中后的实际收益和召回率，必须通过固定基准视频逐项验证，不能仅凭参数名称推断。

## 3. 用户体验决策

### 3.1 模式选择

- 导入页和审核页的“重新分析”入口使用统一的模式选择卡片。
- 普通用户只选择“快速/标准”，暂不直接编辑 FPS、分辨率、阈值等底层参数。
- 分析运行后锁定模式；要换模式，先取消当前任务，再重新分析。
- 开始前显示预计耗时范围，分析中显示阶段、进度和动态剩余时间。
- 审核页显示 `标准分析` 或 `快速分析 · 可能漏检` 徽章。
- 快速模式完成后提供“用标准模式重新分析”，不自动转标准。
- 快速模式零候选时提示可能漏检，并提供标准模式重试，不静默切换。
- 快速结果导出前给出一次非阻塞风险提示，用户仍可继续导出。
- 分析运行期间审核区继续保留上一份已完成候选，并提示“正在生成新的分析结果，当前候选仍可继续审核”。
- 分析运行期间允许继续播放、审核和修改旧候选，不能因为新任务启动而清空候选列表。
- 分析完成前暂不允许导出；如需导出旧结果，先取消新分析。

### 3.2 审核操作保持简单

- 不增加“精修选中候选”功能。
- 不增加单候选精修按钮或批量精修按钮。
- 候选区保留播放、保留/排除、时间范围修改等核心操作。
- 只保留一个统一的“重新分析”入口，点击后再选择模式。

## 4. 任务、结果和失败恢复

- 同一项目同时只允许一个重型分析任务运行。
- 每次重新分析创建新的分析批次。
- 新批次完成并校验成功后，原子切换为当前结果。
- 新批次运行期间继续显示上一个已完成结果。
- 新批次失败或取消，不影响当前已完成结果。
- 主动取消的任务不自动恢复；已完成的代理缓存保留。
- 应用崩溃、强制退出或休眠造成的异常中断，下次打开项目时提示是否恢复。
- 恢复优先复用已校验的阶段产物，从最近安全阶段继续；缓存失效时回退到最近安全阶段重跑。
- 快速模式转标准模式时，标准模式必须重新完整粗扫，不复用快速候选；只允许复用安全的模型、代理和其他参数匹配缓存。

## 5. 缓存与参数可追溯性

- 快速代理和标准代理独立缓存，不互相覆盖。
- 缓存键至少绑定：源视频指纹、代理分辨率、代理 FPS、模型/算法版本和实际分析参数。
- 每个分析批次保存完整参数快照：模式、实际代理规格、精筛开关、模型版本、算法版本和参数配置版本。
- 历史结果必须能够解释当时使用的参数，不能只保存一个 `fast/standard` 标签。

## 6. 耗时记录

耗时按分析批次持久化，并提供两级展示：

**摘要：**

```text
标准模式 · 用时 8 分 32 秒 · 找到 24 个候选
```

**详情：**

- 代理生成耗时；
- 粗扫耗时；
- 候选生成耗时；
- 原视频精筛耗时；
- 预览生成耗时；
- 缓存命中数；
- 候选数量和检测数量；
- 推理设备、模式和实际参数。

当前代码已有任务阶段进度和 checkpoint 基础，优先在现有 `jobs.checkpoint_json` / `analysis_parameters` 路径上补齐，不重复建设任务进度系统。

## 7. 分阶段范围

### 第一期：模式和性能闭环（已落地，基准验证除外）

1. 增加快速/标准模式协议和项目级模式记忆。
2. 固定快速模式代理参数为 `640×480 / 3 FPS`。
3. 快速模式跳过原视频回源精筛。
4. 确保两档代理按参数独立缓存。
5. 保存阶段耗时和完整参数快照。
6. 接入模式徽章、预计耗时、风险提示和统一重新分析入口。
7. 保持新批次原子切换，失败/取消保留旧结果。
8. 保持单项目单重型分析任务。
9. 快速模式先由功能开关控制，质量闸门达标后才对普通用户开放。
10. 新分析期间保留旧候选，成功后再刷新；分析期间不允许导出。
11. 候选默认保留，导出以 `selection_status` 为准；只有已排除候选不会进入输出。

已补充的实现细节：

- 新分析不会先删除旧候选；只有新结果通过产物校验、预览准备并完成写入后才替换。
- 快速模式候选直接从粗扫候选文件生成，并在候选证据 JSON 中记录 `analysis_source: coarse`。
- 标准/快速两种结果使用包含实际参数的独立分析键和代理路径。
- 自动继承只在候选 ID 精确匹配或事件时间 `±2 秒` 的唯一最近邻匹配时发生；人工时间范围平移后会限制在视频时长内。
- 分析期间仍可审核现有候选，但导出入口会锁定，避免导出与候选替换产生竞态。

### 第二期：历史和运维增强

1. 分析历史独立入口，不混入主审核区。
2. 保留最近 5 个批次元数据，最近 2 个完整结果。
3. 支持恢复历史完整快照，包括候选、审核状态、手动时间、备注和球员标签。
4. 标准模式替换快速模式后可展示候选差异，并按已确认的保守规则自动继承可明确匹配的人工状态；有歧义的候选不继承。
5. 提供历史缓存清理和安全磁盘空间管理。
6. 空间不足时在分析前阻止启动，提示可清理内容，不删除原视频和当前结果。

## 8. 验收标准

正式启用快速模式前建立固定基准集，至少覆盖短、中、长视频以及不同编码、画质和典型比赛场景。

每个基准视频分别运行快速和标准模式，记录：

- 总耗时和各阶段耗时；
- 代理缓存命中情况；
- 候选数量；
- 候选时间重叠率；
- 关键片段漏检情况；
- 设备、模型和参数快照。

第一版最低目标：

- 快速模式相对标准模式提速 **40% 以上**；
- 关键片段召回率不低于 **80%～85%**；
- 不改变审核、播放、手动修改和导出流程；
- 快速/标准结果可重复，失败和取消可恢复到旧结果。

如果快速模式未达到召回率底线，优先调整快速参数或暂不开放快速模式，不通过静默改变业务规则来掩盖结果差异。

## 9. 明确暂不做

- 不增加第三档“极速模式”。
- 不在本轮改用更小 YOLO 模型或降低检测阈值。
- 不自动后台继续标准精筛。
- 不限制快速模式候选数量。
- 不做单候选或批量候选精修。
- 不在快速/标准分析并行时允许导出，避免候选替换与导出产生竞态。
- 不在本轮把 Python Engine 整体迁移到 Rust；速度瓶颈仍在 YOLO 推理和视频解码，Rust 迁移不会自动解决这一点。

## 11. 当前已确认的数据契约

- 项目模式设置写入现有 SQLite `settings` 表，按项目保存 `analysis_mode`；新项目默认 `standard`。
- 快速模式的候选直接来自 `coarse_candidates.json`，统一格式化、去重、排序后写入审核结果，并在证据中标记 `analysis_source: coarse`。
- 审核主播放器固定使用原视频路径；`review_video_path` 不再返回分析代理。代理只用于分析和预览。
- 新分析成功时允许自动继承旧审核状态：先按候选 ID 精确匹配，匹配不到时按同视频、同 ROI、事件时间差不超过 `±2 秒` 的一对一最近邻匹配；有歧义不继承。
- 自动继承保留保留/排除、原因、备注和球员标签；审核耗时不继承。未手动修改时间的候选采用新默认时间，手动修改过的时间范围按事件时间差整体平移并限制在视频范围内。
- 第一期不持久化完整历史批次；新任务运行期间保留旧结果，成功后替换，失败或取消继续保留旧结果。
- 快速模式的 `640×480` 表示目标框最大尺寸，保持原视频宽高比；不强行拉伸为 `640×480`。
- 快速模式先隐藏在功能开关后；未通过冷启动提速和召回率闸门时，普通用户只看到标准模式。
- 质量闸门达标后才打开快速模式入口；后续调整快速参数后需要重新验证，不能默认沿用旧结论。

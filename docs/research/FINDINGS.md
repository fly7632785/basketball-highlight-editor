# 代码研究结论

## 1. 最接近目标的算法

`third_party/bball-highlights/pipeline/detect_makes_yolo.py` 已经实现了当前项目最重要的闭环：

```text
固定篮筐校准
  ↓
篮筐附近 ROI
  ↓
YOLO 检测 sports ball
  ↓
保留靠近篮筐的篮球轨迹
  ↓
判断篮球从篮筐上方到下方
  ↓
过滤反弹和重复事件
  ↓
输出进球时间
```

它还实现了：

- 采样帧率控制；
- ROI 推理；
- 批量推理；
- 检测结果缓存；
- 单视频校准失效检查；
- 进球事件去重；
- 手工真值标注和 precision/recall/F1 评估。

## 2. 对我们项目可直接吸收的设计

### 直接保留的思想

- 固定机位和单篮筐限定；
- 每个视频单独校准篮筐；
- 只在篮筐附近运行检测；
- 使用篮球真实检测替代纯橙色像素计数；
- 使用“上方 → 下方”的几何穿越判断；
- 先生成候选，人工审核最终结果；
- 缓存逐帧检测结果，调参数时不重复跑模型；
- 使用人工标注的真实进球计算 precision、recall、F1。

### 需要改造的地方

- 当前仓库默认使用命令行和文件夹结构，需要改成项目任务模型；
- 当前只支持检测后直接生成 reel，需要加入候选审核状态；
- 需要保存用户删除、保留和时间调整结果；
- 需要支持“合并导出”和“单独导出”；
- 需要处理原视频 PTS/time_base，不能只依赖帧号换算；
- 需要将模型和 FFmpeg 依赖抽象，避免桌面实现绑死在单个平台。

## 3. 不建议直接复用的内容

- `OwlTing` 仓库中的旧 YOLOv4/PyTorch/TensorRT 运行环境；
- 未声明许可证仓库中的代码；
- 直接写入视频帧的实时 GUI 逻辑；
- 大量针对某几个时间点调出来的常量；
- 把“篮筐附近出现篮球”直接当作进球的判断；
- 没有真实标注集支持的准确率结论。

## 4. 算法风险确认

即使使用 YOLO，单个斜角固定摄像机也可能无法区分：

- 球从篮筐前方擦过；
- 球从篮筐后方擦过；
- 球真实穿过篮筐但短时被篮网遮挡。

因此人工审核不是临时补丁，而是产品设计的一部分。

## 5. 工程路线调整

第一阶段不强制迁移 Rust，也不强制把 OpenCV 编译到四个平台：

```text
Python + OpenCV + YOLO + FFmpeg
  ↓ 验证真实视频效果
Flutter 审核界面 + Python Worker
  ↓ 固化数据接口和评估集
再决定纯 Rust、C++/OpenCV 或混合原生核心
```

## 6. 纳入外部代码评审后的修订

外部评审与本地代码检查结论一致，项目路线作以下调整。

### 6.1 阶段 1 跳过 HSV 主检测

`bball-highlights/NOTES.md` 已经记录了颜色+运动方案在真实视频中的失败原因：球衣、皮肤、地板会产生橙色噪声，而球穿网时可能只剩极少像素。因此：

- HSV 只保留为调试基线或低成本 fallback；
- 主检测直接采用 YOLO 篮球检测；
- 事件判定采用几何穿越，而不是橙色像素计数。

### 6.2 进球判断采用“双层几何条件”

结合 `bball-highlights` 和 `basketball-shot-detection`：

```text
篮球进入篮筐上方候选区
  ↓
记录最后一个上方点
  ↓
篮球出现在篮筐下方
  ↓
连接上方点和下方点
  ↓
计算轨迹与篮筐高度的交点
  ↓
交点位于篮筐宽度范围内
  ↓
下降方向、速度和反弹检查
  ↓
进球候选
```

这比“篮球靠近篮筐”严格，也比“只从上到下”多了一层横向约束。

### 6.3 篮网运动只作为后续增强

篮网运动可以作为候选加分信号，但不能作为必需条件，因为某些拍摄角度看不到篮网，或者球网被遮挡。第一阶段不把篮网检测放入主路径，待真实数据统计后再决定。

### 6.4 Rust 阶段优先评估 ONNX Runtime

不再默认采用 Rust OpenCV 绑定。候选生产路线改为：

```text
YOLO/专项检测模型
  ↓ 导出 ONNX
Rust ort crate
  ↓
篮球检测结果
  ↓
Rust 几何判断、状态机和任务调度
```

[`ort`](https://github.com/pykeio/ort) 支持加载 ONNX、运行推理并检查 CoreML 等执行提供程序是否可用，但具体 iOS、Android、macOS、Windows 构建仍需用目标平台和真实模型验证，不能仅凭 crate 文档宣称四端可直接发布。

### 6.5 专项模型作为第二阶段方案

COCO `sports ball` 可以先用于基线，但篮球在远距离、运动模糊和遮挡场景下可能检测不足。数据量足够后，优先训练 `basketball`、`rim/hoop` 两类专项模型；是否增加 `person` 类，要由后续产品功能决定，不为当前进球剪辑提前扩大模型范围。

### 6.6 代码复用边界

三个仓库最适合复用的是算法流程，不是完整应用：

- `bball-highlights`：产品流程、缓存和评估闭环；
- `Basketball-Shot-Detection`：轨迹与篮筐几何判断；
- `AI_basketball_games_video_editor`：检测日志和两阶段处理思想。

未声明许可证的仓库不直接复制；即使代码许可证允许，模型权重、训练数据和 Ultralytics 依赖也要单独做分发审查。

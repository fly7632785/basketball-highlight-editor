# 本地运行与资源评估

## 一句话结论

**本地运行可行，当前阶段不需要云端 GPU。**真正的性能瓶颈是目标检测推理，不是 FFmpeg 剪切；但在没有真实视频和目标设备基准前，不把具体倍速、准确率或内存数字写死。

## 当前开发机实测环境

| 项目 | 实测值 | 判断 |
|---|---|---|
| 系统 | macOS 26.1，Darwin arm64 | 已确认 |
| 芯片 | Apple M1 Pro，8 核 | 适合作为桌面端开发基线 |
| 内存 | 16 GB | 足够做单任务离线扫描；不建议同时跑多个模型任务 |
| FFmpeg | 8.1 | 已安装 |
| FFmpeg 硬件能力 | `videotoolbox`、`h264_videotoolbox`、`hevc_videotoolbox` | 当前机器具备硬件解码/编码路径 |
| Python 推理环境 | 项目 `.venv` 使用 Python 3.11.14；`torch`、`ultralytics`、`opencv`、`numpy` 已安装；`onnxruntime` 未安装 | 当前 Python Engine 可运行，ONNX 仍不是 V1 依赖 |

证据来自当前机器的 `uname -a`、`system_profiler SPHardwareDataType`、`ffmpeg -hwaccels` 和 Python 导入检查。硬件编码器可用不等于整条视频处理链自动硬件加速，仍需按实际命令验证。

## Claude 评审中纳入的内容

### 1. 先用轻量模型做基线

正确，但“nano 一定达到几十毫秒”“一定低于视频时长”不能当成验收结论。第一轮应该把模型档位作为变量比较：

- COCO `sports ball` 的轻量模型：验证零训练能否跑通；
- 参考项目的 `yolo11m.pt`：作为已有流程对照，不作为最终模型；
- `basketball-shot-detection` 的 `bball_model.pt`：本地验证专用权重，但模型权重授权尚未独立确认；
- 后续再测试更小输入尺寸或更轻模型。

最终以同一批视频记录 `precision`、`recall`、`F1`、扫描耗时、峰值内存和误报类型，而不是根据模型名称推测性能。

### 2. ROI 和低清代理视频

纳入主路线：固定机位、单篮筐允许先校准篮筐，再只对篮筐附近区域做检测。代理视频可以降低解码和推理成本，但必须保存原始视频与代理视频的时间映射，不能简单用“代理帧号 ÷ 代理 FPS”替代原始 PTS。

建议默认参数作为待测起点，而不是最终配置：

```text
代理分辨率：720p；若球在代理中小于可检测尺寸，再回退 1080p
扫描采样：15 FPS 或每 2 帧取 1 帧
检测区域：篮筐框外扩一定余量
审核预览：原视频按候选时间点精确取片段
```

### 3. 平台加速分层

纳入架构方向，但每个平台都要实测：

| 平台 | 首选推理路径 | 失败回退 |
|---|---|---|
| macOS Apple Silicon | MPS/Core ML/ONNX Runtime provider 中选实际可用者 | CPU |
| Windows | DirectML；有 NVIDIA 时再评估 CUDA | CPU |
| iOS | Core ML | 降低代理分辨率或改为桌面端处理 |
| Android | NNAPI（设备差异大） | CPU；必要时限制视频分辨率 |

第一版不把四个平台的统一加速实现作为前置条件。桌面端先把“任务可恢复、可取消、可审核、可导出”跑通。

## 资源瓶颈拆解

| 环节 | 资源压力 | MVP 判断 |
|---|---:|---|
| 读取/解码 | 中低；取决于分辨率、编码格式和磁盘 | 使用 FFmpeg/系统硬件路径，先不优化到极致 |
| 代理生成 | 中等；长视频会占用磁盘和 CPU | 后台任务，生成后缓存 |
| YOLO 推理 | 最高 | 只跑 ROI、低清代理、采样帧；单任务优先 |
| 轨迹关联与几何规则 | 低 | Python/Rust 均可，暂不是瓶颈 |
| 审核播放 | 中等；取决于同时播放的片段数量 | 逐个预览，不预先生成所有高清片段 |
| FFmpeg 导出 | 中等 | 审核通过后再导出，合并时统一编码参数 |

## 不采用的过度承诺

- 不把社区项目的单机扫描速度直接外推到用户设备；
- 不把“YOLO nano 只有几 MB”作为固定事实，模型格式、版本和量化方式都会改变体积；
- 不把 FFmpeg 硬件解码等同于 YOLO 硬件推理；
- 不把 `YOLO26` 作为当前架构前置依赖，先以已能复现的模型和工具链为准；
- 不把参考项目声称的准确率直接作为本项目验收标准；
- 不在未核查模型权重、训练数据和推理框架许可证前承诺商业分发。

## 必做基准矩阵

用户提供真实视频后，固定同一批输入，至少测以下组合：

| 变量 | 取值 |
|---|---|
| 视频 | 720p/1080p；30 分钟左右；不同光线和遮挡 |
| 代理 | 480p、720p、原始分辨率（仅作对照） |
| 采样 | 10 FPS、15 FPS、逐帧局部复核 |
| 模型 | COCO 轻量模型、`yolo11m.pt`、`bball_model.pt` |
| 执行设备 | CPU、Apple GPU/MPS 或对应可用 provider |

每次记录：总耗时、推理耗时、峰值 RSS、缓存大小、候选数、人工确认的 TP/FP/FN，以及原视频时间戳偏移。

## 当前工程判断

```text
Python + Ultralytics/ONNX + OpenCV + FFmpeg
  ↓ 先在真实视频上得到可重复基准
Flutter 桌面审核界面 + 独立 Worker
  ↓ 再决定推理运行时
ONNX Runtime / Core ML / DirectML / Rust ort
```

**现在不需要因为“本地可能吃资源”而改成云端架构，也不需要立即投入 Rust 或自训练。**先完成一轮真实数据基准，才能决定模型大小、代理分辨率和是否值得做移动端本地推理。

# 篮球集锦编辑器 V1 决策记录

> 本文件是当前产品、算法和工程方案的决策入口。它描述当前代码应保持的边界；历史实验只作为证据，不覆盖运行时事实。

## 当前决策

| 领域 | 当前决策 | 原因 |
|---|---|---|
| 桌面入口 | macOS 桌面端为主路径，Windows 为兼容/实验路径 | 先稳定本地长视频闭环 |
| 移动端 | 独立 Flutter App，不启动桌面 Python Engine | 适配移动端媒体 API 和原生推理能力 |
| 移动端状态 | Android 已接入抽帧 + Rust/ONNX 分析，当前主要验证 `arm64-v8a`；iOS 项目/媒体/导出可用，本地分析等待 Runtime 链接 | 明确“可构建”“可分析”“可发布”的差异 |
| 桌面 UI | Flutter + Material 3；Riverpod 管理项目状态，go_router 管理页面，media_kit 负责播放 | 保持页面、状态和协议边界清晰 |
| 桌面本地引擎 | Python 独立进程，通过 JSONL 与 Flutter 通信 | 复用已验证算法，减少桌面跨平台原生编译成本 |
| 移动推理 | Rust + ONNX Runtime，通过平台 channel/FFI 接入 | 在移动端提供不依赖 Python 的推理路径 |
| 推理策略 | 篮球/篮筐检测 + 几何穿越 + 轨迹/篮网等辅助信号 | 生成高召回候选，不把单一信号当裁判结论 |
| 视频处理 | FFmpeg 负责桌面代理、预览和最终剪辑；移动端使用平台媒体 API | 最终导出尽量回到原视频 |
| 数据 | 桌面 SQLite；移动端项目包保存设置、元数据、候选和审核状态 | 可恢复、可审计、离线可用 |
| 项目范围 | 单项目、单视频、单篮筐、固定机位；Schema 为扩展保留空间 | 降低 V1 UI 和算法复杂度 |
| 原视频 | 默认只引用路径，不复制、移动或自动删除 | 避免大视频重复占用磁盘 |
| 审核 | 候选默认保留，用户排除误检；漏检可通过手动补漏加入 | 保持高召回和可控导出 |
| 任务 | 同一项目同时只运行一个重型分析或导出任务；支持取消、失败、重试和中断发现 | 控制资源并避免状态竞态 |
| 默认片段 | 事件前 6 秒、后 3 秒，审核时可调整 | 覆盖投篮动作和落地结果 |
| 导出 | 桌面支持分别导出和合并导出；移动端支持平台片段导出和保存到媒体库 | 兼顾可用性和平台能力 |
| 隐私 | 默认本地处理、不登录、不上传 | 真实视频和人物数据不离开设备 |
| 分析模式 | 标准质量优先；快速使用 `640×480 / 3 FPS` 代理并跳过原视频精筛；新项目默认标准，按项目记忆选择 | 在不改变审核/导出语义的前提下缩短等待 |
| 分析结果 | 每次重新分析创建新批次，成功后切换；失败/取消保留旧结果 | 防止半成品清空审核区 |
| 分析记录 | 保存阶段耗时、缓存命中、设备和实际参数快照 | 能解释结果并验证性能改动 |
| 快速模式开关 | 当前桌面入口默认可见，也可以用 `ENABLE_FAST_ANALYSIS=false` 隐藏 | 让发布构建可按质量闸门控制入口 |

分析模式的完整参数、缓存和继承规则见 [`research/ANALYSIS_MODES_V1.md`](research/ANALYSIS_MODES_V1.md)。

## 已吸收的开源思路

参考项目只用于理解问题和比较方案，不复制其代码、权重或数据：

| 思路来源 | 吸收内容 | 当前边界 |
|---|---|---|
| 篮球集锦/投篮检测项目 | ROI、跳帧、缓存、粗扫/精筛、候选审核 | 重新实现为本项目 Python/Rust 模块 |
| 篮球轨迹跟踪项目 | 上下穿越、抛物线和篮筐附近轨迹 | 作为辅助信号，不替代人工审核 |
| 体育集锦检测项目 | 运动触发、片段合并、前后时间窗口 | 用于候选去重和性能实验 |
| `ai-sports-cut-agent` 等 Agent 项目 | 将分析、审核和导出分阶段组织 | 不直接引入云端 Agent 依赖 |

完整研究来源和许可证边界见 [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md)。

## 不属于当前发布前置的事项

- 云端同步、账号系统、在线模型服务；
- 端到端时序分类器和大规模自有数据训练；
- 多视频、多篮筐、多机位和实时直播；
- 桌面端把 Python Engine 整体替换为 Rust；
- iOS 本地分析正式发布（当前仍缺少 Runner 原生库链接和目标设备验收）；
- 完成 macOS/Windows 安装包、签名、公证和干净机器验收前的二进制分发。

## 算法结论边界

- 目标是“高召回候选 + 人工审核”，不是无人值守自动剪辑；
- 单个视频上的 Precision 或耗时不能代表跨视频泛化；
- 新算法优先使用按篮筐宽度归一化的参数、留一视频验证和错误类型分析；
- 新信号保留原始证据字段，不直接覆盖历史结果；
- 快速模式如果未通过召回闸门，应关闭入口或调整参数，不通过限制候选数量制造提速。

## 变更规则

改变以下内容时，必须同步更新本文件、对应契约和测试：

1. Flutter 与 Engine 协议；
2. SQLite 或移动项目包数据模型；
3. 未审核候选是否可导出；
4. 原始视频复制、移动或上传策略；
5. Python/Rust/ONNX 推理运行时和模型分发方式；
6. 快速/标准模式的候选来源、缓存键或继承规则。
